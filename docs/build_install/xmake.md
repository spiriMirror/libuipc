# XMake

## Prerequisites

For `pip install -e . --config-settings=builder=xmake`, see
[editable Python development](./dev_in_uv.md) for the complete environment
setup and comparison with CMake's prerequisites.

The following dependencies are required to build the project.

| Name                                                | Version      | Usage           | Import         |
| --------------------------------------------------- | ------------ | --------------- | -------------- |
| [XMake](https://xmake.io/) | >=3.0.5 | build system | system install |
| [Python](https://www.python.org/downloads/)         | >=3.11       | build system    | system install |
| [Cuda](https://developer.nvidia.com/cuda-downloads) | >=12.4       | GPU programming | system install |

## Build Project

Clone the repository with the following command:

```shell
git clone https://github.com/spiriMirror/libuipc.git
```

Then, you can use the following commands to build the project.

```shell
cd libuipc
xmake f -c
```

The default build includes the CUDA backend, examples, and tests. Optional
modules are explicit and disabled by default:

```shell
# Enable either or both optional libraries.
xmake f --usd=true --vdb=true -c

# CPU/interface-only configuration (the none backend still builds).
xmake f --backend_cuda=false -c

# Lean CUDA build: omit legacy comparison/alternate broad-phase filters.
xmake f --cuda_legacy_collision=false -c
```

`--usd=true` resolves OpenUSD 25.08 or newer, and `--vdb=true` resolves a shared
OpenVDB package. XMake's compiler cache is disabled by project policy; use normal
incremental builds rather than enabling ccache externally.

## Troubleshooting

### out of memory

Xmake uses a lot of process for parallel compilation in order to accelerate the compilation task. However, nvcc will consume a lot of memory, thus will eventually cause an OOM

Set the multi-process count manually, for example `xmake -j8` for eight parallel
compilation jobs.


## dev in uv

Use [uv](https://docs.astral.sh/uv/) to manage a virtual environment for Python development. The following steps configure xmake with Python binding support, create a virtual environment, build the project, and package the Python wheel.

```shell
uv venv --seed --python 3.12 .venv
source .venv/bin/activate
xmake f --pybind=true --python_system=true --python_version=3.12.x -c
xmake build -j4
xmake pack -v
```

### Editable install

`xmake pack` produces a wheel, which has to be reinstalled after every change.
For day-to-day development, use an editable install instead. One command drives
xmake through the build backend:

```shell
python -m pip install -e . --config-settings=builder=xmake
```

If the checkout was already built in another mode, match it so the existing
object files are reused instead of recompiling all ~200 CUDA translation units:

```shell
python -m pip install -e . --config-settings=builder=xmake \
  --config-settings=xmake-args="-m releasedbg" --no-build-isolation
```

`--no-build-isolation` skips provisioning a build environment on every install,
which is worth it for repeated rebuilds. It does mean pip ignores
`[build-system].requires`, so the environment needs setuptools and wheel:

```shell
python -m pip install 'setuptools>=64' wheel
```

Omit `--no-build-isolation` on a fresh interpreter and pip provisions everything
for you; the extension is built against the target ABI either way, since the
isolated environment is created from the same interpreter.

Optional settings:

| Setting | Default | Meaning |
| ------- | ------- | ------- |
| `jobs=N` | `4` | Parallel compile jobs. nvcc is memory-hungry; one job per core tends to OOM. |
| `xmake-args="..."` | -- | Extra flags appended to `xmake f`, e.g. `-m release` or `--backend_cuda=false`. |

Without `builder=xmake` or `UIPC_BUILDER=xmake` the install goes through CMake, and
`pip wheel` / `pip install .` always do.

Both editable paths report the development version `0.9.0`: xmake reads it
from `python/pyproject.toml`, and the CMake editable hook supplies the same
value. Non-editable CMake wheels continue to derive their version from Git via
setuptools-scm. This only affects editable development installs, never a
published wheel.

To drive xmake by hand instead, configure `--python_editable=true` and install
`python/`, which carries its own metadata:

```shell
xmake f --pybind=true --python_system=true --python_editable=true -c
xmake build -j4
uv pip install -e python   # once
```

For the pip-driven route, re-run the same pip install command after native
changes. For the manual route, `xmake build` refreshes the extension while
the configuration enables `python_editable` and selects the intended Python
interpreter. Python sources are imported from the working tree.
Note that this mode does not run `scripts/stubgen.py`, so the
`.pyi` stubs under `_native` are only regenerated by `xmake pack`.

Pass every option you care about in a single `xmake f` invocation. Options left
out fall back to their defaults, so `xmake f --python_editable=true` on its own
also resets `--pybind` to `false`. The backend sidesteps this by keeping its
configuration under `build/xmake-pep517`, so `pip install -e .` never clobbers
options set by hand in the checkout. The flip side is that the two
configurations only share object files when their options agree: the backend
builds in `release` unless told otherwise, so a checkout configured as
`releasedbg` recompiles from scratch on the first `pip install -e .`. Pass
`--config-settings=xmake-args="-m releasedbg"` to keep them aligned.

In `releasedbg` mode the install also drops a `pyuipc.sym` symbol file of a few
hundred megabytes next to the extension; build with `-m release` if that matters.
Everything written into `python/src/uipc/_native` is ignored by git except its
`README.md`.
